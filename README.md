# Findev — Realtime Fintech Dashboard

An Angular application with a live market dashboard and producer settings. Simulated market
updates are generated by a Rust library compiled to WebAssembly, running inside a Web Worker.

- **Repository:** https://github.com/Val-Git/findev
- **Live demo:** https://val-git.github.io/findev/

Every push to `main` lints, tests, builds and redeploys the demo to GitHub Pages
(see [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml)).

## Requirements

| Tool                                               | Version                                     |
| -------------------------------------------------- | ------------------------------------------- |
| [Node.js](https://nodejs.org/)                     | 26 (the version used in CI)                 |
| npm                                                | 12 (see `packageManager` in `package.json`) |
| [Rust](https://rustup.rs/)                         | 1.88 or newer (edition 2024)                |
| Rust target `wasm32-unknown-unknown`               | —                                           |
| [wasm-pack](https://rustwasm.github.io/wasm-pack/) | 0.13 or newer                               |

```bash
rustup target add wasm32-unknown-unknown
```

```bash
cargo install wasm-pack
```

Then install the JavaScript dependencies:

```bash
npm ci
```

## Run

```bash
npm start
```

Open http://localhost:4200/. `npm start` first compiles the Wasm library
(`npm run build:wasm`) into `src/wasm/market-gen/`, which is generated and not committed, so
a plain `ng serve` works only after the Wasm library has been built once.

## Build

```bash
npm run build
```

The production build is written to `dist/findev/browser/`. The Wasm binary is copied to
`dist/findev/browser/wasm/`. To build for a sub-path, as the GitHub Pages deployment does:

```bash
npm run build -- --base-href /findev/
```

## Architecture

```text
Angular (main thread)                    Web Worker                         Wasm (Rust)
─────────────────────                    ──────────                         ───────────
DashboardComponent ─┐                    ProducerEngine
SettingsComponent ──┼─ MarketFeedService ──commands──▶ ProducerRun ──nextBatch(n)──▶ Generator
                    │   (single owner    ◀──events────  (timer, totals)  ◀──Int32Array──  (RNG, prices,
                    │    of the worker)   status/snapshot/error                           per-instrument state)
```

### Wasm library — `wasm/market-gen/`

- `Generator` (`lib.rs`) is a thin `wasm-bindgen` wrapper around `MarketGenerator`, which is
  plain Rust and tested with `cargo test`.
- `MarketGenerator` owns the RNG and every instrument's state between calls, and returns
  exactly the requested number of updates. Each update goes to a uniformly chosen
  instrument, so an instrument may appear several times in a batch.
- Each step of an instrument (`instrument.rs`): the bid does a small random walk with a weak
  pull towards its starting price, the ask is the bid plus a spread of at least one cent,
  book quantities random-walk around a base level, and the trade hits either the bid or the
  ask, with buys more likely when the book leans to the bid side.
- The RNG (`rng.rs`) is a seeded SplitMix64 + xorshift64*, so output is reproducible in
  tests. The worker seeds it from `crypto.getRandomValues`.
- All prices are integer cents. A batch is a flat `Int32Array` of 7 integers per update:
  `instrument, priceCents, tradeQuantity, bidCents, askCents, bidQuantity, askQuantity`.
  The worker checks on load that both sides agree on the field count.

### Web Worker — `src/app/core/producer/`

- `ProducerEngine` keeps at most one current `ProducerRun` and forwards commands to it:
  `start`, `pause`, `resume`, `stop`.
- `ProducerRun` loads the generator, requests a batch every `batchIntervalMs`, applies every
  update to per-instrument running totals and posts a snapshot of the dashboard rows after
  each batch. The next batch is scheduled after the current one is processed, so slow
  batches never pile up.
- Running totals (`instrument-accumulator.util.ts`) keep only the latest trade price, latest
  bid/ask, cumulative volume and cumulative `price × quantity`. No event history is
  retained, and every trade contributes to volume and VWAP even though the UI refreshes
  once per batch.
- Pausing clears the timer; resuming schedules the next batch one interval later, so the
  paused interval is not generated. A run's generator and timer are released when the run
  is replaced, stopped or fails.

### Angular — `src/app/`

- `MarketFeedService` is a root singleton created at startup and the only owner of the
  worker, so navigating between pages keeps the active run and creates no extra producers.
- Each `start` carries a new `runId`, and every worker event carries the `runId` of the run
  that produced it. The service drops events from replaced runs, so a late result never
  overwrites the new run's state. `apply` clears the table immediately.
- The status shown on the dashboard is the status confirmed by the worker.
- The settings page edits a local draft (Angular signal forms). Nothing reaches the producer
  until **Apply**, which starts a new run with the new settings, even when the previous run
  was paused.
- Prices are rounded only for display (`CentsCurrencyPipe`). Missing values and zero
  denominators show `—`.

### Project layout

```text

src/wasm/market-gen/           Generated wasm-pack output (not committed)
src/app/core/producer/         Worker code: engine, run, accumulators, Wasm loader
src/app/core/feed/             MarketFeedService: worker owner for the Angular app
src/app/features/dashboard/    Live market table, pause/resume, status
src/app/features/settings/     Validated producer settings form
src/app/shared/                Formatting pipes and helpers
```
